## 1. 파이프라인

```
"야간 자전거 수집해줘"
  │
  ▼ agent      키워드 사전으로 검색어 생성 → y/n 승인
  ▼ collector  수집 → 품질 검사 → 중복 제거 → CLIP 관련성 필터
  ▼ labeler    YOLO 자동 라벨 → 자동 통과 / 검수 대기 / 폐기
  ▼ 사람        검수 대기분만 손으로 고침
  ▼ labeler.split  train / val 분할 + data.yaml
  ▼ training   YOLO 학습 → 평가
```

미니 프로젝트에서 만든 도구 2개(collector, labeler)와 에이전트를 그대로 쓰고, 최종 프로젝트에서 `split`과 `training`을 붙였습니다.

## 3. 학습 실험 (복구 후 데이터 기준)

공통 설정: `yolo11n`, freeze 10, imgsz 640, batch 8, seed 0 고정.

### 실험 A — 학습 설정 바꾸기 (라벨 134장, train 107 / val 27)

| 설정 | epoch | best | mAP50 | mAP50-95 | precision | recall |
|---|---|---|---|---|---|---|
| **학습 전 `yolo11n`** (기준) | — | — | 0.6680 | **0.5356** | **0.8601** | 0.5721 |
| optimizer auto (lr0 0.01) | 100 | 1 | 0.6014 | 0.3919 | 0.6748 | 0.6025 |
| optimizer auto (lr0 0.001) | 21 | 1 | 0.6014 | 0.3919 | 0.6748 | 0.6025 |
| SGD lr0 0.01 | 22 | 2 | 0.6173 | 0.3932 | 0.7836 | 0.5984 |
| **SGD lr0 0.001** | 21 | 1 | **0.6780** | 0.5353 | 0.8334 | **0.6139** |

학습 설정을 어떻게 바꿔도 **학습 전 모델과 비슷한 수준**에 머물렀습니다(mAP50 +0.010). `optimizer`와 `lr0` 조합이 가장 큰 변수였고, 그 내용은 아래 4절에 적었습니다.

### 실험 B — 라벨을 촘촘히 하기 (라벨 148장, train 118 / val 30)

같은 사진 세트에 **검수를 더해 박스를 1,577개 → 1,970개(+25%)로** 늘린 뒤, 실험 A에서 가장 좋았던 설정(SGD lr0 0.001)으로 다시 학습했습니다.

| | best epoch | mAP50 | mAP50-95 | precision | recall | 놓침률 |
|---|---|---|---|---|---|---|
| 학습 전 `yolo11n` | — | 0.6354 | 0.4879 | 0.7924 | 0.5539 | 0.4461 |
| **학습 후** | **5** | **0.6806** | 0.4917 | 0.7260 | **0.6244** | **0.3756** |
| 차이 | | **+0.045** | +0.004 | −0.066 | **+0.071** | **−0.071** |

### 두 실험을 나란히 — 라벨을 촘촘히 한 뒤 개선폭이 커지는 경향 (소규모 검증)

| | 박스 수 | mAP50 개선 | 놓침률 개선 | best epoch |
|---|---|---|---|---|
| 실험 A (라벨 134장) | 1,577 | +0.010 | −0.042 | 1 |
| **실험 B (라벨 148장)** | **1,970** | **+0.045** | **−0.071** | **5** |

라벨을 촘촘히 한 뒤 개선폭이 커졌고, `best epoch`도 1에서 5로 밀렸습니다. 실험 A에서는 1에포크 뒤부터 계속 나빠졌는데(배울 게 없었다), 실험 B에서는 5에포크까지 좋아집니다.

**다만 이것을 "라벨 품질의 효과"로 단정할 수 없습니다.** 실험 A와 B 사이에 바뀐 것이 라벨만이 아니기 때문입니다.

| 바뀐 것 | A → B |
|---|---|
| 박스 수 | 1,577 → 1,970 (+25%) |
| 라벨 장수 | 134 → 148 (+14장) |
| train / val | 107 / 27 → 118 / 30 |
| val 정답 내용 | 더 촘촘해짐 (같은 사진이라도 정답이 달라짐) |

세 가지가 동시에 움직였으므로 **라벨 품질만의 기여를 분리하려면 사진 수와 val을 고정한 채 라벨만 바꿔 비교해야 합니다.** 지금은 그 실험을 하지 않았습니다. 그래서 "라벨 품질이 먼저다"가 아니라 **"라벨을 촘촘히 한 뒤 개선폭이 커지는 경향을 봤다(소규모 예비 실험)"**까지가 지금 말할 수 있는 전부입니다.

**precision은 떨어졌습니다**(0.792 → 0.726). 작고 먼 사람을 잡으려다 오탐도 같이 늘었습니다. 후방 경고에서는 **놓치는 쪽이 더 위험**하므로 받아들일 만한 교환입니다.

### 놓침률 (1 − recall)

후방 경고에서는 **사람을 놓치는 것**이 가장 위험하므로 recall을 뒤집어 봅니다.

| | 놓침률 |
|---|---|
| 학습 전 `yolo11n` (실험 B의 val 기준) | 0.446 |
| **학습 후 (실험 B)** | **0.376** |
| 목표 | 0.3 이하 (아직 미달) |

열 명 중 4.5명을 놓치던 것이 3.8명으로 줄었습니다.

### 이 수치를 믿으면 안 되는 이유 두 가지

1. **val이 27~30장뿐입니다.** 이 정도 차이는 사진 몇 장으로 뒤집힐 수 있습니다.
2. **val 정답이 `yolo11n` 자동 라벨에서 출발해 사람이 고친 것**입니다. 출제자와 응시자가 같은 셈이라 학습 전 `yolo11n`에게 유리합니다.

또 **실험 A와 B는 val 세트가 서로 다릅니다**(27장 vs 30장, 라벨 내용도 다름). 그래서 두 실험의 절대 수치를 직접 비교하면 안 되고, **각 실험 안에서 "학습 전 → 학습 후" 개선폭만** 비교해야 합니다. 실험 B의 학습 전 수치가 더 낮은 것(0.635 vs 0.668)은 모델이 나빠져서가 아니라 **val 라벨이 더 촘촘해져 사전학습 모델이 더 많이 놓치기 때문**입니다.

**공정한 비교는 사람이 처음부터 만든 정답(`gt_rear`)으로 해야 합니다.** 후방 영상 R5를 평가 전용으로 찍어 거기에 쓸 예정입니다.

## 4. 오늘 확인한 것

### Ultralytics `optimizer=auto`는 `lr0`를 무시합니다

처음에 lr0를 0.01 → 0.001로 낮춰 돌렸는데 결과가 소수점까지 같았습니다. 원인은 기본값 `optimizer=auto`였습니다.

```
ultralytics/engine/trainer.py:1224
  "'optimizer=auto' found, ignoring 'lr0=...' and determining best 'optimizer' and 'lr0' automatically"
```

클래스 수가 2이면 `lr_fit = 0.002 * 5 / (4 + 2) = 0.001667`로 정하고 optimizer를 **AdamW**로 덮어씁니다. `--optimizer SGD`를 직접 주고 나서야 lr0가 적용됐고, 그제야 위 표의 네 번째 줄이 나왔습니다.

이걸 모르고 두 실험이 같다는 이유로 "데이터가 문제"라고 결론지을 뻔했습니다.

### 라벨은 사진보다 비쌉니다

PC 포맷으로 `data/labels`와 gt100 v2가 날아갔습니다. 사진은 Wikimedia pageid가 파일 이름에 들어 있어 API로 다시 받을 수 있었지만(출처·작가·라이선스까지 121장 전부 복구), **손으로 그린 라벨은 Roboflow에 올려 둔 덕분에 겨우 살렸습니다.**

| 잃은 것 | 복구 | 방법 |
|---|---|---|
| 사진 | O | 이름의 Wikimedia pageid로 재다운로드 |
| `metadata.csv` 출처·라이선스 | O | Wikimedia API 조회 (121줄) |
| 검수 라벨 134장 | O | Roboflow 프로젝트에 남아 있던 것 |
| gt100 v2 정답 세트 | **X** | 복구 못 함 |
| 학습 기록 (`results.csv`) | **X** | 복구 못 함 |

교훈: **라벨은 레포 밖 어딘가에 반드시 복제본을 둔다.**

후방 영상은 삼각대로 렌즈 높이 100cm, 아래로 약 15°(앞 3.7m 지점이 화면 중앙)에서 찍습니다. 승용차 번호판 높이를 그대로 재현한 설정입니다. COCO 사진과 화각·높이·조명이 달라, 여기서는 학습 효과가 더 크게 나올 것으로 봅니다. 그 가설을 검증하는 게 다음 목표입니다.

밝기는 장소로 나눕니다 — **R1 덜 어두운 곳(학습), R2 어두운 곳(학습), R5 다른 장소(평가 전용)**. 파일명 끝에 밝기를 붙여(`20261112_R1_01_보행접근_덜어두움.mp4`) `rear_report`가 밝기별 감지율을 따로 냅니다. 한 세트는 클립 8개(보행 접근·횡단·멀어짐, 자전거 접근·횡단, 어두운 옷 접근, 여러 명, 빈 장면)입니다.

다만 **영상은 프레임이 많습니다.** fps 2로 뽑으면 1분짜리 영상에서 120장이 나오고, R1~R4면 수백~수천 장입니다. 전부 손으로 라벨할 수는 없으므로, 자동 라벨로 먼저 깔고 **신뢰도가 낮은 것만 검수 대기열로 올리는**(`review_queue.csv`) 지금 방식이 그대로 필요합니다. 실험 B가 보여 준 "라벨 품질이 먼저"라는 결론과, 그 라벨을 감당 가능한 양으로 줄이는 도구가 이 프로젝트의 두 축입니다.

단 **R5의 `gt_rear`만은 전부 손으로 만듭니다.** 자동 라벨에서 출발하면 위에 적은 "출제자와 응시자가 같은" 문제가 되풀이됩니다.

## 부록: 재현 방법

```bash
# 1. 수집
python -c "from collector import run_collector; print(run_collector(['night bicycle','night cyclist','night person','night pedestrian'], count_per_query=20))"

# 2. 자동 라벨
python -m labeler run

# 3. 검수한 라벨만 모아 분할 (Colab으로 옮기려면 --portable)
python -m labeler.split --labels data/labels_reviewed --out data/dataset_v3

# 4. 학습 (gt100 v2가 없으면 --skip-eval)
python -m training.train --data data/dataset_v3/data.yaml --name v3_sgd_lr0001 \
    --skip-eval --optimizer SGD --lr0 0.001 --patience 20

# 5. 학습 전 모델과 비교
python -c "from ultralytics import YOLO; print(YOLO('yolo11n.pt').val(data='data/dataset_v3/data.yaml', imgsz=640, classes=[0,1]).box.map50)"
```

환경: Python 3.11, ultralytics 8.4.211, torch 2.14.1+cu126, GTX 1060 3GB.
`--optimizer`, `--lr0`, `--patience`, `--skip-eval`은 PR #53, `--group-by round`와 `--portable`은 PR #54에 있습니다.
